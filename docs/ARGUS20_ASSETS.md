## 1. ExpoPlatform (Tampereen Messut: Verkosto, Alihankinta)

**Назначение.** JSON-API каталога экспонентов, который вендор ExpoPlatform отдаёт на собственном домене каждой ярмарки Tampereen Messut. Источник числа экспонентов для сверки полноты (поле `total` в ответе — это число организатора, не наша оценка).

**Эндпоинт.**
- `POST https://<домен-ярмарки>/api/v1/search/exhibitors` — список, тело `{"page": N, "limit": 60}`.
- `POST https://<домен-ярмарки>/api/v1/search/filters` — справочник залов/категорий (опционален, тело `{"type": "exhibitors"}`).
- Домен — **домен самой ярмарки** (`verkostomessut.fi`, `alihankinta.fi`), НЕ `api-<tenant>.expoplatform.com` (этот хост отдаёт 401 на `/admin/`) и НЕ домен группы `tampereenmessut.fi`.

**Аутентификация.** Нет. Публичный каталог, без ключа, без cookie.

**Пагинация и лимиты.** Сервер сам ограничивает страницу 60 записями независимо от запрошенного `limit` (100 и 500 в запросе всё равно вернут 60). Обход должен ориентироваться на `total` в ответе и на пустую страницу как признак конца, а не на собственную арифметику по `limit`. Страница за концом списка отвечает 200 с пустым `list`, не 404.

**Пример запроса (curl, без ключа):**
```
curl -X POST "https://verkostomessut.fi/api/v1/search/exhibitors" \
  -H "Content-Type: application/json" -H "Accept: application/json" \
  -d '{"page":1,"limit":60}'
```

**Пример ответа (реальный, curl выполнен 2026-09-17 19:05 UTC):**
```json
{"code": 200, "data": {"total": 126, "list": [
  {"id": 1221, "external_id": "062319", "name": "ABB Oy", "url": "abb-oy-0c6a8482",
   "about": "", "city": null, "country": null, "stands": [ ... ]}
  // ещё 59 записей на странице 1
]}}
```
Ключи одной записи: `id, external_id, name, about, url, city, country, region, stands[], category_id, objectType, role, is_parent_exhibitor, count_child_exhibitors, is_pavilion, isNew, logo, owner_id`. Публично нет сайта/e-mail/телефона экспонента — их каталог не отдаёт нигде, только через форму на детальной странице за логином. `alihankinta.fi` в этот же момент отдал `total: 1078`.

**Известные грабли.**
- 2026-08-30: ранний аудит принял хост `api-tamperefairs.expoplatform.com` за рабочий эндпоинт по аналогии со SPA-фронтом; это неверно — он требует авторизации (401) и не является публичным каталогом.
- 2026-09-14 (STATUS.md, 5 прогонов подряд 08:31–08:58 UTC): маршрутизация внутри системы несколько раз вообще не вызывала обращение к этому источнику за прогон («route never invoked»), хотя сам эндпоинт был доступен и отвечал — дефект был в правиле выбора маршрута выше по стеку, не в контракте API.
- Наблюдался случай, когда базовый хост для запроса брался не с домена самой ярмарки, а с домена группы (`tampereenmessut.fi`) — на этом домене каталог не отвечает; правильный хост — домен конкретной ярмарки текущего года.

**Стоимость.** Бесплатно (публичный HTTP, без квоты, без ключа).

## 2. Messukeskus WordPress

**Назначение.** Список экспонентов и карточки экспонентов для ярмарок на площадке Helsingin Messukeskus, отдаётся как обычный WordPress REST API кастомного типа записи.

**Эндпоинт.**
- `GET https://<slug>.messukeskus.com/wp-json/wp/v2/exhibitors?lang=<fi|en>&per_page=100&page=N` — список (custom post type `mk_exhibitor`, REST `rest_base=exhibitors`).
- `GET https://<slug>.messukeskus.com/wp-json/wp/v2/types` — справочник типов, чтобы подтвердить `rest_base`.
- Каждое событие живёт на СВОЁМ поддомене (`finnbuild.messukeskus.com`, `habitare.messukeskus.com`), НЕ на `www.messukeskus.com/en/exhibitors/<slug>/` — человекочитаемая страница списка там пустая (гидратируется JS), реальные данные только через wp-json.
- Ссылка на карточку конкретного экспонента берётся из поля ответа `link`, а не собирается по шаблону — реальный путь на разных сайтах отличается (`.../exhibitors/<slug>/`, `.../naytteilleasettajat/`, `.../yritykset/<slug>/`).

**Аутентификация.** Нет.

**Пагинация и лимиты.** Стандартная WP REST-пагинация: заголовки ответа `X-WP-Total` (общее число) и `X-WP-Totalpages`. `per_page` до 100.

**Пример запроса (curl, без ключа):**
```
curl "https://finnbuild.messukeskus.com/wp-json/wp/v2/exhibitors?lang=en&per_page=5&page=1"
```

**Пример ответа (реальный, curl выполнен 2026-09-17 19:05 UTC):**
- Заголовки: `X-WP-Total: 421`, `X-WP-Totalpages: 85`.
- Тело (обрезано):
```json
[{"id": 11982, "link": "https://finnbuild.messukeskus.com/en/exhibitors/design-agency-elisa-wirkkala-oy/",
  "title": {"rendered": "Design Agency Elisa Wirkkala Oy"}, "acf": {...}, "mk_product_group": [...],
  "mk_theme": [...], "translations": {...}, "lang": "en"}]
```
Ключи записи: `id, link, title, content, acf, meta, mk_product_group, mk_theme, slug, status, translations, lang, pll_sync_post, date, modified, _links`. Также в этом ответе сайт вернул заголовок `x-wp-doingitwrong` — предупреждение WordPress о постороннем маршруте `custom/v1/programs` без `permission_callback`; к каталогу экспонентов отношения не имеет.

**Известные грабли.**
- 2026-08-17: контракт с полем «I love me» скомпилировался в DAG с именем венью «Messukeskus» вместо имени события — эвристика «первое слово с заглавной» приняла площадку за выставку (CLAUDE.md, инвариант 9). Подтверждённых участников тогда упало с 84 до 37 после исправления.
- 2026-08-17: `habitare.messukeskus.com` классифицировался как «наш» `event_site`, потому что проверка принимала любой поддомен `messukeskus.com` — Habitare это чужая мебельная выставка того же организатора; её экспоненты рисковали получить grade A как «наши».
- Дважды наблюдался прогон, где `source_url` копил несколько страниц организатора в статусе `pending`, которые ни разу не обходились ни одним воркером (не проблема API, проблема очереди обхода).

**Стоимость.** Бесплатно.

## 4. Jyväskylä Paviljonki

**Назначение.** Портал зала Jyväskylän Paviljonki — читается как «страница площадки» (`venue_page`, класс источника уровня grade A), а не через отдельный API; плюс PDF-планы залов, которые парсятся отдельным модулем.

**URL-паттерны (подтверждено вживую, домены `paviljonki.fi` / `jklpaviljonki.fi` / `jyvaskylanpaviljonki.fi`):**
- `https://www.paviljonki.fi/messut/<событие>/` — главная страница ярмарки.
- `https://www.paviljonki.fi/messut/<событие>/kavijoille/naytteilleasettajat/` (FI) и `.../en/messut/<событие>-2/for-visitors/exhibitors/` (EN) — страница со списком экспонентов.
- Год выставки не в URL, а на самой странице (в тексте/логотипе, например `finnmateria_2026_logo_...png`) — из URL год не извлечь надёжно.

**Аутентификация.** Нет, обычный публичный сайт (WordPress-тема `paviljonki`).

**Пример запроса (curl):**
```
curl -L "https://www.paviljonki.fi/messut/finnmateria/kavijoille/naytteilleasettajat/"
```

**Пример ответа (реальный, curl выполнен 2026-09-17 19:06 UTC):** HTTP 200, `<title>Näytteilleasettajat - Paviljonki</title>`, 345 КБ HTML; прямых PDF-ссылок на этой конкретной странице не найдено (список экспонентов на ней текстовый/HTML, не PDF) — планы залов, если есть, следует искать по соседним разделам сайта (`/tilat/`, отдельные страницы зала), это не проверено в рамках одного запроса.

**Известные грабли.**
- `finnmateria.fi` (домен самого события) отдаёт 301 на страницу внутри `paviljonki.fi` — именно там, а не на «своём» домене, лежат сектор, даты и зал ярмарки; проверка «это домен нашего события» не должна отбрасывать `paviljonki.fi` как чужой домен площадки, когда на конкретной странице по факту назван зал.
- PDF-планы/каталоги читаются отдельным парсером многоколоночного текста: архив издания «Materia» (`vuorimiesyhdistys.fi`, не сам Paviljonki, но тот же класс PDF-документов) был свёрстан в две колонки, и построчный порядок из базовой PDF-библиотеки их перемешивал, плюс перенос слова по слогу на границе строки склеивал половины разных предложений в одно «название компании». Правило починки — восстанавливать порядок чтения по координатам колонок, а перенос — по слогу, а не полагаться на порядок операторов в потоке PDF.

**Стоимость.** Бесплатно.

## 5. Wayback CDX

**Назначение.** Чтение индекса архивных URL Internet Archive для домена ярмарки — источник имён экспонентов из снятых с публикации старых страниц (например, каталог издания прошлого года, которого уже нет на живом сайте). Читается только CDX-индекс (список URL с меткой времени), не сами архивные страницы.

**Эндпоинт.** `GET https://web.archive.org/cdx/search/cdx` с параметрами:
```
url=<домен без www>/*
output=json
fl=original,timestamp,statuscode
collapse=urlkey
filter=statuscode:200
from=<год>
to=<год>
limit=<N>
```
`collapse=urlkey` схлопывает повторные захваты одного URL в одну строку; `filter=statuscode:200` отбрасывает редиректы и 404.

**Аутентификация.** CDX read API в коде вызывается БЕЗ ключа/токена — публичный эндпоинт. В архивных `.env`-файлах есть `IA_ACCESS_KEY` / `IA_SECRET_KEY` (учётные данные Internet Archive S3-подобного API), но по коду репозитория они нигде не читаются и не используются этим или каким-либо другим модулем — похоже на задел на будущее (например, Save Page Now) либо неиспользуемые переменные; для CDX-чтения не нужны. **Для карточки 18/реестра ключей 2.0: стоит пересмотреть, нужны ли эти два ключа вообще.**

**IPv4-требование.** В коде явного принудительного IPv4 (pinning) не найдено. Проверить вживую в этой сессии не удалось: у машины, где выполнялась проверка, нет маршрута в IPv6 вообще (`curl -6` → «Could not resolve host» независимо от archive.org), поэтому подтвердить или опровергнуть особенность archive.org с IPv6 технически нельзя. Помечено как непроверенное, без домысливания.

**Пагинация и лимиты.** Лимит по умолчанию — 2000 строк на один вызов, таймаут вызова — 30 секунд (CDX — «тяжёлая» часть 30-секундного бюджета фазы первого света). Один вызов на домен через общий лимитер вежливости.

**Пример запроса (curl, без ключа):**
```
curl "https://web.archive.org/cdx/search/cdx?url=verkostomessut.fi/*&output=json&fl=original,timestamp,statuscode&collapse=urlkey&filter=statuscode:200&from=2024&to=2025&limit=15"
```

**Пример ответа: не проверено сейчас.** Два вызова curl 2026-09-17 19:06–19:07 UTC подряд вернули HTTP 503 с телом `Internet Archive: Temporarily Offline` — сервис был недоступен в момент проверки (проверено и с `-4`, и без флага, оба раза 503 от самого archive.org).

**Обновление 2026-09-24 (шаг 3.6, живая проверка Sonnet A).** CDX снова отвечает: `curl "https://web.archive.org/cdx/search/cdx?url=verkostomessut.fi/*&output=json&fl=original,timestamp,statuscode&collapse=urlkey&filter=statuscode:200&from=2024&to=2025&limit=15"` → HTTP 200, реальные строки (`api/v1/dict/...`, `assets/dist/css/...` со штампами вида `20250204130458`). Значит 503 от 17.09 был временным — сервис перемежающийся, что и фиксирует известная грабля ниже, не сломанный контракт. IPv6-вопрос по-прежнему не проверен (машина без IPv6-маршрута); код форсирует IPv4 явно (`httpx.HTTPTransport(local_address="0.0.0.0")`).

**Известные грабли.**
- STATUS.md фиксирует случай восьми подряд `httpx.ReadTimeout` на CDX-вызовах в одном такте — архив периодически отвечает медленно/не отвечает, это штатный повод для повтора/деградации, а не сигнал сломанного контракта.
- Модуль Wayback на ветке `v2/graph-first-run` реализован полностью (отдельный источник + отдельный воркер); в более раннем состоянии проекта его не было — карточка 6 «Common Crawl» из ТЗ снята отдельно и в среде 2.0 сознательно не нужна.
- Найденное — кандидат, не факт: имя из архивного URL пишется как кандидат компании, участие в ТЕКУЩЕМ издании выставки всё равно должно подтвердиться отдельной цитатой; архивный список прошлого года — доказательство того года, не текущего.

**Стоимость.** Бесплатно (публичный API archive.org, без квоты); зависит от доступности сервиса.

## 7. Serper

**Назначение.** Прямой доступ к «сырой» выдаче Google (SERP JSON) для фразового поиска — единственный из поисковых каналов, который реально видит индекс Google, а не SearXNG-агрегацию. Первый в приоритете фразового поиска, потому что закрывает дыру: датацентровый IP через SearXNG не достаёт то, что достаёт Google API.

**Эндпоинт.** `POST https://google.serper.dev/search`, тело JSON: `{"q": "<запрос>", "num": 1..20, "hl": "<lang, опц.>"}`.

**Аутентификация.** Заголовок `X-API-KEY`. Имя ключа в реестре: `SERPER_API_KEY`. Ключ едет в заголовке, не в query-строке (важно: у Google CSE — наоборот, своего заголовка нет).

**Пагинация и лимиты.** `num` — максимум 20 результатов за один вызов, паджинации сверх этого нет (не «страницы», а размер выдачи). Ходит напрямую, без прокси (правило CLAUDE.md §«Сеть»: поисковые каналы и краулинг не через Hiddify/forward-proxy).

**Пример запроса (curl без ключа):**
```bash
curl -s -X POST https://google.serper.dev/search \
  -H "X-API-KEY: $SERPER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"q": "Messukeskus Helsinki exhibitors", "num": 3}'
```

**Пример ответа (реальный, проверено 2026-09-17 19:08 UTC):**
```json
{"message":"Not enough credits","statusCode":400}
```
Счёт на момент проверки пуст (см. «Известные грабли» — это состояние тянется с 13–14.09 и на дату архивации не изменилось). Не «не проверено»: HTTP 400 с этим телом — реальный текущий контракт сервиса при пустом балансе.

**Известные грабли (с датами).**
- **CIRCUIT-1 (найдено 13.09.2026).** До фикса `HTTP 400 "Not enough credits"` от Serper уходил в общий транспортный отказ и не отличался от временного сбоя сети — окно здоровья не видело бюджетного отказа как бюджетного, и один и тот же факт «денег нет» переигрывался повторно на каждом запросе. За 13.09 это дало часть из 80 минут прогона без результата на трёх параллельных прогонах. Фикс: HTTP 400 с телом, содержащим «not enough credits» (без учёта регистра), классифицируется отдельным типом отказа — раньше общей проверки `>= 400`.
- **2026-09-13 19:40 / 2026-09-14 08:58–14:xx.** Баланс Serper — отрицательный, «400 Not enough credits» стабильно; это НЕ блокирует прогоны (`OWNER_QUEUE #12`), потому что фразовый поиск деградирует на SearXNG — деградация тише, но не останавливает граф. Пополнения баланса за время наблюдения зафиксировано не было.
- Отказ по капче/защите от ботов определяется и по HTTP 451, и по вхождению строки `captcha` в тело ответа независимо от статуса — не только по коду.

**Стоимость.** Тарификация Serper — постранично по числу запросов (не по токенам); точный текущий прайс не зафиксирован в коде/доках проекта (см. google.serper.dev pricing на дату использования). На момент архивации баланс исчерпан, актуальную цену планового пополнения проект не фиксировал.

## 8. OpenRouter

**Назначение.** Единственный платный LLM-шлюз для «сильных» вызовов (generative discovery/поиск, extraction fallback) — один ключ вместо нескольких прямых адаптеров по отдельности. OpenAI-совместимый протокол.

**Эндпоинты.**
- `POST https://openrouter.ai/api/v1/chat/completions` — основной вызов.
- `GET https://openrouter.ai/api/v1/auth/key` — остаток лимита по ключу.
- `GET https://openrouter.ai/api/v1/models` — публичный каталог моделей и цен, **ключа не требует**.

**Аутентификация.** Заголовок `Authorization: Bearer <key>`. Имя ключа в реестре: `OPENROUTER_API_KEY`. Дополнительные заголовки атрибуции (не секрет): `HTTP-Referer: https://argus.gridex.fi`, `X-Title: GRIDEX ARGUS`.

## 10. Docling / PDF-OCR

**Статус: Docling НЕ использовался.** Текст из PDF читала библиотека `pypdf` (`pypdf>=5.1`), чистый Python, без бинарных зависимостей, ~0.5 МБ. Docling в реестре движков помечен `planned` и вызывается по имени только там, где отсутствует («docling не собран») — то есть код называет отсутствующую возможность по имени вместо того, чтобы молча выдавать пустой результат.

**Решение и дата.** Зафиксировано как архитектурное решение, 08.09.2026. Причина отказа от Docling: он тянет `torch`; на сервере (gridex-tools-01) на тот момент было свободно ~5 ГБ диска, установка Docling с зависимостями не помещалась. Альтернатива — либо переполнить диск (под отдельным бюджетом и мониторингом), либо откладывать бессрочно; откладывать признано равносильным «никогда», поэтому выбор сделан явно, а не по умолчанию.

**Что это закрыло и что нет.**
- Закрыто: PDF с текстовым слоем (каталоги, программы, планы залов *с текстовым слоем*) читается бесплатно и локально, без вызова модели; evidence-ссылка несёт номер страницы и ненулевой чанк.
- Не закрыто: OCR для сканов (страниц без текстового слоя) — компания остаётся в статусе ожидания с причиной «docling не собран», уходит в Gap Register. Многоколоночная вёрстка (планы залов) — `pypdf` отдаёт текст в порядке потока содержимого, не порядка колонок; для двухколоночных PDF (пример — архив журнала Materia, `vuorimiesyhdistys.fi`) это ломало порядок чтения, что и породило отдельный модуль перестановки колонок поверх `pypdf`, а не переход на Docling.

**Когда по плану пересматривалось.** Два условия (любое): (1) на сервере появится ≥8 ГБ свободного диска под `torch`, и в Gap Register накопятся сканы; (2) многоколоночные PDF начнут регулярно уходить на платный маршрут модели чаще, чем окупает структурный разбор Docling. Ни одно из условий на дату архивации (17.09.2026) не отмечено выполненным.

**Стоимость.** $0 (`pypdf` — локальная библиотека, без внешнего API). Docling не установлен — стоимость не применима.

## 11. Crawl4AI — вывод для ARGUS 2.0: нужен, но требует своей операционной обвязки с первого дня

**Вывод: httpx + Playwright «в лоб» не заменяют Crawl4AI без переноса той же операционной работы, которая уже была проделана поверх Crawl4AI — а прямого адаптера на Playwright в старой системе никогда не было и не тестировалось.**

**Обоснование.**

1. **Playwright не использовался напрямую нигде.** Единственная прямая зависимость на HTTP-транспорт в проекте — `httpx>=0.27`; зависимости `playwright` в проекте нет вообще. Всё JS-рендеринг и антибот-обход шли исключительно через контейнер `unclecode/crawl4ai:latest` (собственный пул браузеров внутри образа). Значит «достаточно ли httpx+Playwright» — вопрос без прямого прецедента в этом кодовом остатке: заменять пришлось бы не готовый прямой канал на другой готовый прямой канал, а строить новую browser-pool-обвязку с нуля.
2. **Реальная проблема была не в рендеринге, а в управлении одним общим контейнером под параллельной нагрузкой.** Три параллельных прогона 13.09.2026 разогнали контейнер до 1049 Chromium-процессов / 83% памяти / 166% CPU (при штатных 70–500 процессов / 20–45% память) — потому что вежливый rate-limit «один запрос на домен» не является квотой на конкурентность: прогон, трогающий 200 доменов, может держать 200 одновременных фетчей и не нарушить ни одного правила по домену. Это второй по счёту кризис контейнера за те же сутки.
3. **Проблема закрыта на уровне оркестрации, а не заменой инструмента**, тремя независимыми, последовательно введёнными механизмами (все с датами 13–14.09.2026): (а) снижение пула самого контейнера; (б) сторож-таймер — перезапуск контейнера при превышении порога процессов/памяти, с cooldown; (в) более быстрое реле поверх сторожа (такт 10 с против 2 мин у сторожа), потому что память успевала пройти путь 60%→99.6% за 2 минуты — быстрее, чем реагировал сторож. После введения всех трёх состояние было отмечено как ожидающее верификации живым прогоном (обязательное условие для следующей приёмки по правилу владельца, CLAUDE.md §Автономия п.6) — т.е. на момент архивации фиксация решения существует, но окончательное «работает под нагрузкой» ещё не подтверждено отдельной записью verified.
4. **Практический смысл для 2.0.** Если 2.0 сохраняет контейнеризованный Crawl4AI (он в зафиксированном стеке ARGUS 2.0, CLAUDE.md, раздел «Краулер»), то перечисленные три механизма — обязательная часть первого деплоя, а не дополнение «когда будет время»: без них любой прогон с более чем одним одновременным исследованием повторит инцидент 13.09 — компонент тот же самый. Замена Crawl4AI на прямой Playwright-пул — это смена технологии из зафиксированного стека и по правилу CLAUDE.md требует отдельного явного вопроса владельцу; здесь дана только фактическая база для этого решения, не рекомендация его принять.

**Стоимость.** $0 (self-hosted контейнер, не платный API); стоимость не денежная, а ресурсная (память/CPU/процессы хоста) — и именно она была источником трёх инцидентов за одни сутки.

## 19. legacy_line_hashes.txt — CI-гейт check_legacy

Отдельный файл: `/mnt/argus-data/argusold-archive/legacy_line_hashes.txt`.

**Метод (решение принято автономно, без вопроса владельцу — см. ниже почему).** Взяты все файлы из `git ls-files` репозитория `/opt/argus-archive-ro` (ветка `v2/graph-first-run`), кроме документации/данных/бинарников/lock-файлов (`.md, .txt, .csv, .jsonl, .json, .svg, .png, .xml, .gz, .example, .gitignore, .dockerignore`, `package-lock.json` и аналогичные lock-файлы) — то есть код и конфиг (py/ts/tsx/js/jsx/mjs/sh/yaml/yml/toml/ini/html/css/mako/ps1, юнит-файлы systemd, Dockerfile/Caddyfile без расширения).

Для каждой строки: **из строки удаляются ВСЕ пробельные символы** (не только края — весь пробельный мусор, включая отступы), и если результат ≥ 40 символов — считается `sha256` от этой очищенной строки (UTF-8). Решение удалять весь пробел, а не только края: делает гейт устойчивым к переформатированию/переотступам в новом коде 2.0 — иначе достаточно сменить отступ, чтобы одна и та же скопированная строка перестала совпадать по хэшу.

Формат файла: один hex-дайджест sha256 на строку, порядок — порядок файлов из `git ls-files`, затем порядок строк внутри файла. Текста строк и путей файлов в выходном файле нет.

**Факты прогона (2026-09-17):**
- файлов рассмотрено: 1203 (из 1726 отслеживаемых git-ом, после исключения нерелевантных расширений)
- файлов прочитано успешно: 1203 (0 пропущено как бинарные/нечитаемые)
- строк просмотрено всего: 402853
- хэшей записано: 147561 (134144 уникальных)
- размер файла: 9.2 МБ

**Назначение.** CI-гейт `check_legacy` для ARGUS 2.0: любая строка нового кода, чей sha256 (после удаления всех пробелов, при длине ≥40) совпадает с хэшем из этого файла — сигнал прямого копирования строки из старой системы, подлежит ручной проверке перед мержем.
