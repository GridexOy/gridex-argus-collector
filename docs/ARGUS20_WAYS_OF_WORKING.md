# ARGUS 2.0 — Как работаем

**Дата:** 03.10.2026 · **Правка:** 03 · **Владелец:** Игорь · Действует во всех блоках и дополняет §2–3 ТЗ блока 0.

Изменения 03: роль «Исполнитель-2 (сборщик Selain)» в отдельном репозитории на Windows (§1); цикл сборщика с «ок» по этапу (§2); потолок разработки сборщика (§9, требует «ок»).

## 1. Роли
- **Владелец (Игорь)** ставит цель, прокликивает интерфейс, говорит «ок» или даёт правки. Код не читает.
- **Исполнитель** — одна сессия Claude Code в `/opt/argus20`. До блока 2 это Sonnet без субагентов. С блока 2 при необходимости подключается Fable как координатор, а субагенты распределяются так: Sonnet на код, Haiku на grep, подсчёты и проверки ссылок. Fable никогда не пишет код и не гоняет тесты.
- **Исполнитель-2 (сборщик Selain)** — одна сессия Claude Code (Sonnet) на Windows MAIN-PC в репозитории `gridex-argus-collector`. Работает по `ARGUS20_TZ_SELAIN.md`. К `/opt/argus20`, серверу и проду доступа не имеет; с ARGUS общается только через контракт `ARGUS20_COLLECTOR_OPENAPI.json`. Серверный модуль `collector` пишет исполнитель ARGUS в блоке 6.
- **Архивариус** — отдельная read-only сессия в `/opt/argus-dev` (Sonnet). Отвечает карточками фактов, см. `ARGUS20_ARCHIVIST_REQUEST.md`.

Две пишущие сессии никогда не работают в одном репозитории.

## 2. Цикл шага (без исключений)
Ветка `block-N/step-M-<slug>` от `main` → сделал → тесты и гейты → закоммитил → поднял VERSION → fast-forward в `main` (только основная сессия) → `deploy.sh` с `main` → удалил ветку step → проверил версию на экране → сдал (шаблон §14 ТЗ блока 0) → **стоп**, ждёт «ок».

Правка шага идёт по тому же циклу. Ветка с тем же именем создаётся заново от `main`, последняя цифра VERSION поднимается.

Версия: `0.<блок>.<шаг>.<правка>`. Первая сдача шага — `.0`. Тег `v0.<блок>.<шаг>` ставится при деплое `.0`; деплои правок тега не получают и опознаются по хэшу коммита на экране.

**Сборщик Selain:** тот же цикл с заменами: ветка `stage-S/step-M-<slug>`, версия `0.<этап>.<шаг>.<правка>`, тег `cv0.S.M`, «деплой» = `install.ps1` на MAIN-PC из `main`, версия видна в панели сборщика. «Ок» владельца — по этапу S0–S6 (решение 03.10.2026); внутри этапа шаги не копятся вне `main`, но сдаются одной тест-картой этапа.

Запрещено:
- деплоить не из `main`;
- копить шаги;
- деплоить грязное дерево;
- мержить не fast-forward;
- начинать следующий шаг «пока владелец проверяет» (для сборщика — следующий этап);
- сообщать «задеплоено» без сверки версии.

## 3. Без вопросов
Если неясно, исполнитель решает сам и пишет: «принято решение X — поправь, если не так». Вопросы владельцу допустимы только когда решение необратимо: удаление данных, платный сервис, изменение критерия G.

## 4. Никаких ночных цепочек
Handoff делается при 85 % контекста, в фиксированной форме: блок/шаг, сделано, не проверено, следующий шаг, расход. Новая сессия читает handoff и документы и **ждёт «ок»**, сама не продолжает. Если «ок» нет 24 ч, она ничего не делает.

## 5. Карантин старого кода
- `/opt/argus-dev` для исполнителей не существует: не открывать, не читать, не копировать.
- Если нужен факт о внешнем сервисе (эндпоинт, авторизация, пагинация), исполнитель задаёт вопрос Архивариусу и получает карточку факта без кода. Ответ добавляется в `docs/ARGUS20_ASSETS.md`, чтобы не спрашивать второй раз.
- Значения секретов переносит владелец. Исполнитель делает `.env.example` и останавливается там, где нужен реальный ключ. Токен сборщика вносит владелец в панель сборщика.
- CI падает в двух случаях:
  - импорт вне `argus20`/`api`/`web` (для сборщика — вне `argus_collector`);
  - 3 и более подряд строк, чьи хэши есть в `docs/legacy_line_hashes.txt`.
- Файл `docs/legacy_line_hashes.txt` генерирует Архивариус (карточка 19). Он кладётся в оба репозитория.

## 6. Агенты (с блока 2)
- Параллельно работают не больше 4 агентов. Пишущих в код — не больше 2, и в разные модули.
- Субагенты не выполняют git; коммитит и мержит только основная сессия.
- Результат агента исполнитель проверяет сам (тесты, diff) до сдачи.
- Если агент предлагает «переделать подход» вместо задачи, результат отклоняется.
- Расход в каждой сдаче: агент → модель → токены → €.

## 7. Регрессия и откат
- С блока 4 gold P/R входит в CI. Мерж блокируется, если R ухудшается больше чем на 5 п.п. или P < 0.9.
- Перед блоком ставится тег `block-N-start` (сборщик: `stage-S-start`). Если блок не принят за 2 попытки — откат на тег, отчёт, решение владельца.
- Тесты предыдущих блоков прогоняются в каждом деплое.
- Контрактные тесты сборщика (`collector/tests/contract/`) подключаются в CI ARGUS в блоке 6; расхождение контракта — красный мерж.

## 8. Kill switch
Файл `/opt/argus20/STOP` проверяют перед каждым шагом любой прогон и любой агент. Если файл есть — остановка с записью в лог. Для сборщика — файл `STOP` в корне `gridex-argus-collector` и кнопка «Pysäytä» в панели.

## 9. Потолки
- **Разработка ARGUS** (Claude Code, исполнитель, субагенты, Архивариус): Anthropic €150 на всё до блока 8. Если остаток < €10 — стоп и отчёт. Рантайм в этот потолок не входит.
- **Разработка сборщика Selain** (исполнитель-2): предложено отдельные €150 до S6 — платный ресурс, действует после «ок» владельца.
- **Рантайм:**
  - Scout-вызовы Anthropic идут по отдельному ключу, пишутся в `model_call` и входят в потолок прогона.
  - Все модели рантайма (OpenRouter, Anthropic, OpenAI, Perplexity, Google, Serper) считаются только по `model_call` в EUR.
  - Локальная модель сборщика пишется в `model_call` с `cost_eur = 0` и токенами; облачный fallback сборщика — `campaign_cloud_budget_eur` в policy задания, по умолчанию 0.
- **Dry-run:** €10/день, €5/прогон, по всем провайдерам рантайма.
- **Диск:** если `/` занят больше чем на 85 % — стоп. Сборщик: диск MAIN-PC > 85 % — стоп новых загрузок, outbox продолжает.

## 10. Приёмка
Приёмка — это владелец прошёл тест-карту и написал «ок». Тестовые проекты остаются в базе с меткой dry-run и скрыты по умолчанию. Для сборщика тест-карты этапов — `ARGUS20_TZ_SELAIN.md` §13.
