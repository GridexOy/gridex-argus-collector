## 1. Контекст
ARGUS 2.0 пишется полностью с нуля. Из старой системы не копируется и не импортируется ни одна строка кода. Старая система служит только источником уроков — списком ошибок, которые нельзя повторить (§3).

Исполнитель работает только в `/opt/argus20`. Доступа к старому дереву нет, и он не нужен: в блоке 0 нет ни одной зависимости от старого кода или данных.

## 2. Подход: Walking Skeleton
Система растёт по одному логическому шагу. Каждый шаг:
- сразу виден в интерфейсе;
- работает насквозь: клик → API → база → экран;
- сдаётся с тест-картой: Игорь прокликивает и говорит «ок» или даёт правки;
- следующий шаг не начинается до «ок».

### 2.1. Цикл шага — обязателен всегда, в каждом блоке
Шаг — это одно логическое изменение, которое видно в интерфейсе. Шагов «только бэкенд», «только рефакторинг», «подготовка на потом» не бывает. Если результат нельзя увидеть и прокликать, шаг нарезан неправильно — перенарезать.

Цикл выполняется без пропусков и перестановок:
1. **Ветка.** `git switch -c block-<N>/step-<M>-<slug>` от актуального `main`.
2. **Сделал** код шага и самопроверку.
3. **Тесты и гейты** (§12) зелёные на ветке.
4. **Закоммитил.** Незакоммиченное не мержится и не деплоится.
5. **Поднял версию** в файле `VERSION` (§5.3), тем же или отдельным коммитом на ветке.
6. **Влил в `main`:** `git switch main && git merge --ff-only <ветка>`. Мерж делает только основная сессия. Если fast-forward невозможен — rebase ветки на `main`, повтор п.3.
7. **Задеплоил** на argus.gridex.fi через `deploy/deploy.sh`, находясь на `main`.
8. **Удалил ветку step** локально и на remote.
9. **Проверил сам глазами,** что в интерфейсе внизу слева новая версия и новая дата.
9а. **Прошёл тест-карту шага сам** в реальном браузере (Playwright + Chromium) на проде, тем же способом, что владелец. Результат по строкам — в сдачу. Без этого шаг не сдаётся (WAYS §2.1).
10. **Сдал владельцу:** версия, что изменилось на экране, что кликнуть (2–5 строк).
11. **Стоп.** Ждёт «ок» или правки.

Правка по замечаниям владельца проходит тот же цикл. Ветка создаётся заново с тем же именем от `main`, поднимается последняя цифра версии (`0.0.3.0 → 0.0.3.1`), коммит пишется как `block-N step-M fix-K: …`.

Запрещено:
- копить несколько шагов и сдавать пачкой;
- деплоить не из `main` или с незакоммиченными изменениями;
- мержить не fast-forward;
- сообщать «задеплоено», не сверив версию на экране;
- сдавать без живой проверки в браузере;
- сдавать правку по части пунктов;
- начинать следующий шаг, «пока владелец проверяет».

Шаги блока 0 (каждый — отдельная ветка, коммит, мерж, деплой и сдача):

| Шаг | Версия | Что видно в интерфейсе |

| 0.1 | 0.0.1.0 | Оболочка: сайдбар, меню (Projektit активен, остальные TYÖN ALLA), флажки, строка версии с датой; справа заголовок Projektit. Списка и кнопки создания ещё нет — и их нет на экране |

## 3. Неподвижные правила (действуют во всех блоках)

### Правило №1. Интерфейс — основной инструмент проверки качества работы. Игорь код не читает.
1. Интерфейс всегда на 100 % соответствует коду.
2. Всё, что видно и выглядит активным, работает. Заглушек, моков, временных решений, демо-данных нет.
3. Всё, что показано, — реальное состояние из базы на момент показа.
4. Чего нет в коде, того нет на экране, либо оно явно помечено как неактивное.
5. Ошибка показывается как ошибка. «Пусто» и «не удалось загрузить» — разные состояния и выглядят по-разному.

### Правило №2. Интерфейс — отдельная надстройка над логикой.
1. Интерфейс можно переделывать (раскладка, цвета, компоненты, тексты), и логика при этом не меняется и не ломается. И наоборот.
2. Единственная связь между интерфейсом и логикой — контракт API (OpenAPI-схема FastAPI). TypeScript-типы и клиент фронта генерируются из неё, руками не пишутся. Если контракт изменился, сборка фронта падает, пока фронт не приведён в соответствие.
3. В интерфейсе нет бизнес-логики: он показывает то, что пришло из API, и отправляет действия. Правила (уникальность, нормализация, статусы, подсчёты) живут только в API.
4. В API нет ничего про показ: никаких пользовательских текстов, переводов, форматов дат. API отдаёт коды и данные.
5. Внутри фронта то же разделение. Вид (компоненты) получает данные только через props и сам никуда не ходит. Данные (хуки) ходят в API.

### Правило №3. Всё дробится на маленькие изолированные модули.
Правки возможны, только когда каждый блок отдельный; иначе получается каша — это главный урок старой системы.
1. Один модуль = одна ответственность = одна папка. Имена говорят, что внутри.
2. У модуля есть публичный вход (контракт) и внутренности. Другие модули пользуются только входом. Нарушение проверяется сборкой.
3. У каждой таблицы БД ровно один модуль-хозяин. Остальные получают данные через его вход.
4. Модуль можно переписать целиком, не трогая остальные, пока не меняется его вход.
5. Файл ≤ 200 строк, функция ≤ 40 строк. Больше — дробить.
6. Принято решение — поправь, если не так. «Мини-сервис» — это изолированный модуль с жёстко проверяемой границей, не обязательно отдельный контейнер. Отдельный контейнер заводится, только когда нужен свой рантайм (web, api, db; позже — воркеры поиска). Вынести модуль в контейнер потом — механическая операция, граница уже есть.

### Правило №4. Документация ведётся вместе с кодом, в том же коммите.
1. `docs/ARGUS20_MODULES.md` — реестр модулей: имя, что делает, вход, выход, какими таблицами владеет, кто вызывает, с какой версии.
2. `README.md` в папке каждого модуля (≤ 40 строк): зачем, контракт, чего не делает, как проверить отдельно.
3. В начале каждого файла — комментарий 1–3 строки: что это и зачем.
4. `docs/ARGUS20_CHANGELOG.md` — запись на каждую версию, включая правки: версия, дата, что изменилось на экране, какие модули затронуты.
5. Шаг без обновлённой документации не сдаётся; это проверяет сборка.

### Уроки старой системы → правила 2.0
| Ошибка в старой системе | Правило 2.0 |
|---|---|
| Сессии сами объявляли «готово» по своим скриптам | «Готово» объявляет только Игорь. Тесты исполнителя — самопроверка |
| 5 проектов «Verkosto 2027» в списке | Дубль названия запрещён на уровне БД |
| Счётчики противоречили друг другу | У каждого значения на экране ровно один источник |
| Сырые i18n-ключи и enum-коды в интерфейсе | Все строки через i18n; сборка падает, если ключа нет |
| e2e-тесты писали в боевую базу | Тесты только с argus20_test; иначе отказываются стартовать |
| После действия экран не обновлялся | После любого действия — немедленный REST-refetch |
| Данные удалялись/перезаписывались | Ничего не удаляется |
| «Починил одно — сломал другое» | Правила №2 и №3, границы проверяет сборка |
| Непонятно, что где лежит | Правило №4 |
| Агенты работали в общем дереве и деплоили что попало | Ветка на шаг, fast-forward в `main`, деплой только из `main` |

### Режим работы исполнителя
- Вопросов не задаёт. Если неясно, решает сам и пишет: «принято решение X — поправь, если не так».
- Субагенты не выполняют git-команд; коммитит и мержит только основная сессия.
- Значения секретов переносит Игорь. Исполнитель делает `.env.example` и останавливается там, где нужен реальный секрет.
- Никаких ночных автономных цепочек.

### 5.3. Сайдбар — низ
**Переключатель языка.** Три флажка в ряд: FI · EN · SV.
- Флаги — встроенные SVG, не emoji (на Windows emoji-флаги не рисуются).
- FI активен и подсвечен.
- EN и SV серые, `aria-disabled`, клик ничего не делает, tooltip TYÖN ALLA.
- Локаль всегда `fi`, префикса в URL нет.

**Строка версии** обязательна, всегда, на всех экранах. Располагается сразу под флажками, мелким серым:
```
v0.0.3.1 (17.9.2026 klo 14.32)
a1b2c3d
```
- Первая строка: версия и в скобках дата-время последнего обновления (момент сборки образа, Europe/Helsinki).
- Вторая строка, мельче: короткий хэш коммита.
- Назначение: владелец одним взглядом видит, обновилась система или нет.

**Правила версии:**
- Источник — файл `VERSION`, формат `0.<блок>.<шаг>.<правка>`, всегда четыре числа.
- Первая сдача шага — `.0` (`0.0.3.0`). Каждая правка того же шага поднимает последнее число (`0.0.3.0 → 0.0.3.1`). Новый шаг сбрасывает правку в 0 (`0.0.3.2 → 0.0.4.0`); это не номер для блока 0, а пример правила.
- Сравнение версий — покомпонентно, как кортеж из четырёх целых.
- Ветка и тег привязаны к шагу, не к правке: ветка `block-<N>/step-<M>-<slug>`, тег `v0.<N>.<M>` (§11).
- Версия, хэш и дата вшиваются в образы API и web при сборке (build args). Вручную не вписываются, из git в рантайме не читаются.
- На экране показываются значения из `GET /api/health`.
- Если версия web ≠ версии API, строка красная и показывает обе: `web 0.0.3.1 / api 0.0.3.0`.
- Если `/api/health` недоступен, показываются версия web и красное `API ei vastaa`.

## 7. Стек
- **Frontend:** Next.js (App Router) + TypeScript + Tailwind + shadcn/ui + lucide-react + next-intl.
- **Backend:** FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic.
- **БД:** PostgreSQL 16, отдельный контейнер и том.
- **Контейнеры:** Docker Compose. Версии закреплены: lock-файлы, образы по digest.
- **Reverse proxy:** существующий Caddy на хосте (не в контейнере).

## 8. Данные
Одна таблица `project`, одна миграция Alembic:
```
id              uuid PK, default gen_random_uuid()
name            text NOT NULL            -- как ввёл пользователь, после trim
name_normalized text NOT NULL UNIQUE     -- trim + схлопнуть пробелы + casefold
status          text NOT NULL default 'created', CHECK (status IN ('created'))
created_at      timestamptz NOT NULL default now()
```
- `verkosto 2027` и `Verkosto 2027` считаются одним проектом → 409.
- Колонок «на будущее» нет.
- DELETE и UPDATE в блоке 0 нет ни в API, ни в коде.

## 9. API
Префикс `/api`. Формат ошибок: `{"code": "<english_snake_case>", "detail": "<english text>"}`.

| Метод | Путь | Ответ |
|---|---|---|
| GET | /api/health | 200: status, db, version (`0.N.M.K`), commit, built_at; при недоступной БД — 503 |
| GET | /api/projects | 200: список id, name, status, created_at, сортировка created_at DESC |
| POST | /api/projects | тело {name} → 201 проект; 409 project_name_exists; 422 validation_error |

- Имя после trim имеет длину 1–120.
- Уникальность обеспечивает БД (UNIQUE), а не предварительный SELECT. Гонка двух запросов даёт один 201 и один 409.
- Фронт ходит по относительному `/api/...` (один origin, без CORS).

## 11. Деплой
### Контейнеры и порты
- Compose-сервисы: `argus20-db`, `argus20-api`, `argus20-web`. Больше ничего.
- Порты только на loopback (принято решение — поправь, если заняты): web `127.0.0.1:4020`, api `127.0.0.1:9020`. БД наружу не публикуется.
- Том БД — на локальном диске.

### Caddy
- Caddy на хосте, argus.gridex.fi:
  - `/argusold*` → старая система (не трогать);
  - `/api/*` → :9020;
  - остальное → :4020;
  - basic-auth на весь сайт.
- Перед правкой Caddyfile: бэкап с датой, `caddy validate` до reload, diff в отчёт.

### Git
- **`main`** — единственная ветка, из которой деплоится прод. Прямых коммитов в `main` нет: только `merge --ff-only` из ветки step, выполняет основная сессия.
- **Ветка step:** `block-<N>/step-<M>-<slug>`, живёт от начала шага (или правки) до мержа, после мержа удаляется локально и на remote.
- **Коммиты:**
  - шаг — `block-N step-M: <что видно на экране>`;
  - правка — `block-N step-M fix-K: <что изменилось на экране>`.
- **Теги:**
  - `v0.<N>.<M>` — ставится `deploy.sh` при деплое версии `0.N.M.0`; правки `0.N.M.K` (K ≥ 1) тега не получают и опознаются по хэшу;
  - `block-N-start` — ставится вручную перед блоком.

### `deploy/deploy.sh`
Это единственный способ деплоя. Шаги по порядку:
0. Отказ, если текущая ветка не `main`: «deploy from main only».
1. Отказ, если локальный `main` не совпадает с `origin/main` после fetch или не является его fast-forward: «main diverged».
2. Отказ, если не прошли сборочные гейты (§12).
3. Отказ, если рабочее дерево грязное: «uncommitted changes — commit first».
4. Отказ, если `VERSION` не в формате `0.N.M.K` или не больше (покомпонентно) версии, которая сейчас отвечает на `/api/health`: «bump VERSION first».
5. build (version / commit / built_at → build args обоих образов) → `alembic upgrade head` → up.
6. Проверка: `/api/health` = 200, и version + commit равны только что собранным. Иначе — ненулевой код выхода.
7. Если K = 0 — `git tag v0.N.M`. Если такой тег уже есть — отказ «step tag exists — bump fix number».
8. `git push origin main` (+ тег, если поставлен).
9. Итоговая строка: `DEPLOYED v0.0.3.0 a1b2c3d 2026-09-17T14:32+03:00`.

Обходных флагов (`--force`, `--skip-*`) нет.

Ветку step удаляет основная сессия после успешного `deploy.sh`.

### Бэкапы
Ночной pg_dump базы argus20 в `/mnt/argus-data/backups/argus20/`, хранить 14 дней.

## 12. Самопроверка исполнителя (не приёмка)
**API (pytest, БД argus20_test):**
1. health → 200, есть commit, version в формате `0.N.M.K`.
2. пустой список → [].
3. создать → 201 → первым в списке.
4. точный дубль → 409.
5. дубль с другим регистром и пробелами → 409.
6. пустое / пробелы / 121 символ → 422.
7. два параллельных POST с одним именем → ровно один 201.

`conftest.py` падает, если имя БД в DSN не оканчивается на `_test`.

**Сборочные гейты** (если хоть один упал — деплоя нет):
- `check_i18n`: каждый использованный ключ есть в `fi.json`; лишних ключей нет.
- ESLint `react/jsx-no-literals`: текст в JSX только через i18n.
- `check_no_cyrillic`: кириллицы нет нигде, кроме `docs/`.
- Границы модулей: import-linter (api), ESLint `no-restricted-imports` / `import/no-restricted-paths` (web) по §10.
- Контракт: `gen_api_client.sh` перегенерирует клиент; если `git diff` не пуст — падение.
- `check_docs`: README у каждого модуля, строка в `ARGUS20_MODULES.md`, запись текущей VERSION в changelog.
- `check_size`: файл ≤ 200 строк, функция ≤ 40.
- `check_version`: `VERSION` в формате `0.N.M.K`.
- `check_legacy`: нет 3 и более подряд строк, хэши которых есть в `docs/legacy_line_hashes.txt`. Если файла ещё нет — гейт пропускается с предупреждением в отчёте.
- `tsc --noEmit`, `ruff`, `pip-audit`, `npm audit --omit=dev` (high/critical = падение).

**E2E** (Playwright, один сценарий, тестовый стек): открыть → пусто → создать → карточка → reload → карточка на месте → дубль → сообщение об ошибке.

```
Что изменилось: <1–2 строки, что видно в интерфейсе>.
Модули: <какие затронуты; какие новые>. Документация обновлена: да.

Решения: <если были>.
Расход: <агент → модель → €>.
Жду «ок».
```

В конце блока исполнитель пишет `docs/ARGUS20_BLOCK0_REPORT.md`:
1. Сделано — 5–8 строк, без кода.
2. Принятые решения.
3. Отклонения от ТЗ (или «нет»).
4. Diff Caddyfile.
5. Самопроверка: pytest / гейты / e2e — числа.
6. Версия на проде: строка DEPLOYED …, вывод `/api/health`, список тегов `v0.0.*`, подтверждение, что веток `block-0/*` на remote нет.
7. Ссылка + тест-карта.

Слово «готово» не используется. Формулировка: «сдан на проверку».
